# CompraForever Route Modality — Route Computed Outside the Game, Quantities Redone In-Game & a Lua-vs-JS Parity Test

> Foto de 2026-11-26 de uma página do second brain do Guilherme (criada em 2026-11-23, atualizada em 2026-11-23), em inglês. Não é atualizada aqui: quando o código e esta página discordarem, vale o código.

Design record of the "route modality" of the CompraForever addon (0.3.0, `C:\GMS\Claude Code Projects\wow\modder\addons-proprios\CompraForever\`): taking the six crafting professions up to skill 150 or 225 along the route computed by the out-of-game tool, with the purchases made "ultra simple" (owner's request, literal: "Eu quero que essas compras sejam ultra simples igual foi no leatherworking também"). Scope of the whole page: `[product: wow-modder]` unless a section says otherwise. **Status (updated 2026-11-23, night):** the modality ran in the game for the first time the same night, on the paladin Ignatius, Engineering 1 to 150 (section 7; commit `990b5e2`, no push). Until then nothing of it had run in the game (commit `66d5aef`).

## Key points

### 1. The route is computed outside the game; the quantities are redone in the game from the real skill `[product: wow-modder]` (n=1)
- The addon does **not** recompute the route (which recipe in which skill band). It receives a skeleton generated by the tool (`legado.mjs`, `estimativas.mjs`): steps, recipes with yellow/grey skill and points, the source of each item per stretch, a ceiling price per unit. In the game it redoes, from the real skill, the bag and the mailbox, how many crafts are still missing and what to buy, and returns the same plan format the action button already executed.
- The owner's flow became one command: Full scan, `/reload`, "atualiza" (`estimativas.mjs` redoes the calculation, generates `Dados.lua` and checks it), `/reload`.
- **Parity test, Lua against JS.** `ferramentas\compra\testar-rota.mjs` runs the Lua function (fengari) over the real `Dados.lua` and compares it step by step with the crafts the JS wrote: R20 gave `74 passos, 0 divergencias`. A mutation test (one craft swapped) proved it catches a difference; that mutation lived in the session's temporary folder (`evidence: perishable`).
- On review, `testar-rota.mjs` ended `casos=20 erros=1` (the one failure is the time case R19, see section 2) and R20 reproduced `74 passos, 0 divergencias`.
- Limits: n=1. **Status as written on 2026-11-23 (evening), updated by section 7 (a status change, not a contradiction of a lesson):** "nothing of the modality ran in the game" held only until the owner's first run that night; the design above is unchanged, but one profession (Engineering), one character, is now in-game evidence. Evidence: `addons-proprios\CompraForever\CONTRATO.md:399` (section 12.4); `ferramentas\compra\testar-rota.mjs:786` (R20); `node ferramentas/pregao/estimativas.mjs` → `checar-dados: ok`; commit `66d5aef`.

### 2. A fixed time ceiling in a performance test under fengari is fragile `[product: wow-modder]` (n=1 machine)
- R19 of `testar-rota.mjs` (119 replans under 1000 ms) passed with 706 to 748 ms during the session and, hours later on the same machine, took 1,501 to 2,210 ms in five runs (two of the session, three of the gate). The code did not change in a way that explains the doubling; the machine load did.
- **Owner's decision (2026-11-23 20:48):** replace the fixed ceiling with a per-replan average with slack (the session applies it in the project; not applied by this ingest).
- Limits: n=1 machine; the cause of the slowness (power, load) was not isolated. Evidence: `node ferramentas/compra/testar-rota.mjs` → `FALHA R19 desempenho ...: 119 replanejamentos levaram 1501 ms` and `1595 ms` (session runs at 20:45); case R19 in `ferramentas\compra\testar-rota.mjs`.

### 4. A handoff step "Agent: run X" that rewrites data ran alone in a `/retomar` session `[product: wow-modder]` (n=1)
- The handoff of the front listed, among the next steps, "Agente: `node estimativas.mjs`" (the "Full, `/reload`, atualiza" flow of section 1). A second session in the same folder received from the owner only `/retomar custo-legacy-profissoes`; seeing the new Full on disk (20:41, written by the `/reload` of 20:48) it announced "Rodando a atualização das estimativas" and ran `estimativas.mjs` by itself, rewriting the addon's `Dados.lua` and `rotas.json` while the first session was doing the `/sb` in the same folder.
- Why the `/retomar` rule ("if the request only says to go back to the subject, summarize and wait") did not hold it: the step was written as the agent's own task, not as a request from the owner.
- **Lesson:** a handoff step that rewrites data or generated files must say who triggers it ("when the owner asks 'atualiza'") and the condition ("no other live session in the folder", checked in `~/.claude/sessions`). The 20:54 version of the handoff already conditions the step. The concurrent-writer side is in AI-Assisted Work Process (the section on committing a repository another session writes to).
- **Cousin, same night (2026-11-23, 22:19; n=2 in `[product: wow-modder]` with the paragraph above):** the first session itself rewrote the same generated files (`rotas.json`, `Dados.lua`) outside the "Full, `/reload`, atualiza" protocol, in answer to an information question; see section 11 below and the cross-pointer in AI-Assisted Work Process (2026-11-23 night section). Context: the "atualiza" protocol had already been agreed with the owner at 22:17 and the session bypassed it (T:626, T:673). Different trigger (own initiative on a question, not a handoff step), same effect.
- **Restore barred, generated files inconsistent (recovered by the gate, checked by the session; n=1).** Before editing `precos.json` the session copied the original to its scratchpad (`precos-antes-tigerseye.json`, T:685), which made a restore possible. The restore was barred by the auto-mode classifier (T:886), so the generated files stayed inconsistent: `Dados.lua` modified and left out of commit `990b5e2` (`git status` shows ` M`), and `precos.json` still with the Tigerseye at 12 s, recorded as a pending item (`estado.md:125`). Limits: the copy lives in the session scratchpad, which a reboot can clear; the next `estimativas.mjs` without `--sem-baixar` rebuilds `precos.json` from the network.
- Limits: n=1. The result was valid output of the same chain (only a newer Full), so the cost was confusion and a parity test that went from 74 to 72 steps, not wrong data. Evidence: other session's transcript `71ac47ff-1a92-4e3c-9c06-c51d58bb82e4.jsonl`, line 12 (`/retomar custo-legacy-profissoes`, 23:45:52Z), line 144 ("O Full das 20:41 já está no disco (o `/reload` gravou às 20:48). Rodando a atualização das estimativas.", 23:48:59Z) and line 145 (the command, 23:49:00Z); `HANDOFF-custo-legacy-profissoes.md` as of 19:35 (commit `66d5aef`), step 2 of "Próximos passos"; `dados\pregao\relatorios\legado-225-2026-11-23-2049.md:3`. Recovered by the gate, checked by the session.

### 5. A panel anchored to a window that closed stayed loose on the screen: a defensive fix, cause not isolated `[product: wow-modder]` (n=1)
- The CompraForever panel anchors to the right of whichever window is open (auction house, vendor, profession, mail, trainer), chosen by flags that the open and close events change. After the trainer closed, the panel stayed in the middle of the screen, anchored to a hidden window (a frame anchored to a hidden frame that is not its parent stays visible). Owner, 2026-11-23 21:21: "Outra coisa, essa janela está orfã" (T:365, with a screenshot).
- The fix does not depend on the flag: it anchors only to a window with `IsShown()` (`naTela`, `Painel.lua:389`), re-evaluates on the window's own `OnHide` (`HookScript`, one per window, `:503`) and again 0.1 s after each event (`C_Timer.After(0.1, reavaliar)`, `:578`), because a Blizzard window can open after the listener in the same event.
- **Defensive correction, cause not isolated.** The stuck flag was not identified (trainer or profession; the event listeners are in the right order in the TOC). Scenario `rota-27` proves only, on the bench's fake, that `OnHide` hides the panel; there was no test against the old code, and the trainer case was not reproduced in the game after the fix. In the game the fix loaded and the panel opened right at the auction house at 22:47. Bench: `node ferramentas/guia/pregao/bancada-pregao.mjs --addon addons-proprios/CompraForever --cenarios rota` → `RESUMO cenarios=29 erros=0`.
- Limits: n=1. Evidence: `Painel.lua:389, :503, :578`; scenario `ferramentas\guia\casos-pregao\cenarios\rota\rota-27-painel-solto-e-scan.lua`; commit `990b5e2`.

### 6. The Forever profession window lists unlearned recipes in "Unlearned > Learnable now"; the trainer's own filter can hide the learnable ones `[product: WoW Forever]` (n=1)
- The profession window of the Forever client lists the recipes that are not yet learned under "Unlearned > Learnable now", with the source (Trainer, Vendor, Drop) and the nearest trainer. The trainer window uses the standard client filter, which can hide the learnable recipes (owner, 2026-11-23 21:55: "ignore, é que estava mostrando só as receitas unavailable", T:600; the word "Settings" appears only in text the session wrote, so the option's name was not seen).
- What happened: the owner read the list as already-learned recipes and concluded that the addon trained by itself ("Ou tá muito estranho pois ele está treinando sozinho sim! Eu não comprei nenhuma receita mas eu estou com todas elas agora", 21:52). What settled it this time (n=1, not a general rule): the gold dropped exactly 5 s (5g 60s 96c to 5g 55s 96c, the price of Journeyman Engineering) and the addon code has no training call (`Grep "BuyTrainerService|TrainerService|C_Trainer|LearnSpell|BuyMerchantItem"` in `addons-proprios\CompraForever\*.lua` → only `Compra.lua:592: BuyMerchantItem`).
- Limits: n=1. Evidence: `C:\GMS\Claude Code Projects\wow\comum\referencia\api-forever.md:164`; the Grep above; owner quotes (T:600).
